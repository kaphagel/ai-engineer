# ADR-0005: From the hopper template to general weldment operations; meaning of an editable native model

- **Status:** Accepted by the product owner, 2026-11-23 (spec §3.5 and §12.1 updated)
- **Date:** 2026-11-23
- **Related:** spec §3.5, §10.7, §12.1, §12.3, §12.4, §12.5, §25 Phase 1 and GE-01 to GE-08, X-04; ADR-0001 (notes 13–16), ADR-0004; PROJECT_STATUS open decision of 20 Nov
- **Evidence:** [spikes/freecad-varset](../../spikes/freecad-varset/); review of [ghbalf/freecad-ai](https://github.com/ghbalf/freecad-ai) (ADR-0001 notes 13–16)

## Context

The Phase 1 hopper is generated by template `esp.hopper` 0.6.0 (ADR-0004). The worker owns the hopper geometry: `hopper_geometry.py` and `hopper_profiles.py` (about 1,100 lines of pure Python) derive panel outlines, profile axes, brackets and bracing from the job parameters, and `templates/esp_hopper.py` turns them into static `Part::Feature` solids, measures them, writes the BOM, flat patterns, drawing and exports. The domain package (`iaiep_esp.hopper`) validates the inputs, resolves the rules, calculates the same quantities with a separate implementation and checks the model against it.

Spec v2.0/v3.0 changed the target:

- Templates are optional accelerators, not the design model (§12.3, §12.4). New configurations are expressed as data, rules, EDM content and combinations of general geometric operations.
- **GE-04** (§25): substantially different proportions or a different panel arrangement must be generated from general operations "without new hopper-specific code".
- §3.5 and §12.1 require native models to stay "editable". On 20 Nov the question was left open whether the template definition may count as the parametric definition, because the saved FCStd file has static shapes.

Two questions follow:

1. **Where does hopper-specific geometry live, and how is CAD built?**
2. **What does "editable native model" mean for generated models?**

What we already have points to an answer for question 1. The FreeCAD calls in the worker are few and generic: a plate from a 3D outline and a thickness, a profile from a section along an axis, a tube, a cut by a plane, a clip against a wall, a compound, and measurements. Everything hopper-specific is the plain-Python calculation of outlines and axes.

For question 2 the spike tested two ways to make the native file follow parameters (FreeCAD 1.1.4, worker image, two sloped hopper walls):

- **Built-in objects only** (`App::VarSet`, fully constrained sketches with constraint expressions, a placement expression, `Part::Extrusion`): exact geometry after build, after parameter changes and after reopening in a fresh process; the file needs no code of ours. Cost: about 40 lines per plate type instead of 5, every relationship written a second time in FreeCAD's expression language, and expressions cannot change the number of objects (tiers, stiffeners, brackets).
- **Scripted features** (`Part::FeaturePython`): exact with our Python module installed. Without it the file opens and looks editable, but a parameter change **silently keeps the old geometry** with no error state.

## Options

### Question 1: CAD construction

| Option | Description | Assessment |
|:---|:---|:---|
| **1A** Keep the template | Worker owns hopper geometry, as now | Every new arrangement needs worker code: fails GE-04 and §12.3. Hopper knowledge is split between worker and domain package |
| **1B** Operation plan of general weldment operations | The domain package generates a plan of typed, general operations; the worker executes any plan | Meets GE-04 for arrangements expressible with the operations. Worker becomes equipment-independent. Plan is recorded and replayable (§12.3, §12.5) |
| **1C** Model writes the plan or code | An LLM produces coordinates or FreeCAD code | Rejected: no numerical authority for the model (§11.1); unrestricted code (§12.3) |

### Question 2: editable native model

| Option | Description | Assessment |
|:---|:---|:---|
| **2A** Regenerated model | The FCStd file is a generated output with static shapes. It can be opened, inspected and measured. Changes go through the inputs (EDM) and regeneration | Keeps the EDM authoritative (§10.7) and every change traceable. Not editable by changing a value in FreeCAD |
| **2B** Expression-driven built-in model | Main dimensions in a VarSet, geometry bound by expressions (spike variant A) | Editable in any FreeCAD for fixed topology. A third implementation of the geometry relationships; no topology changes; hand edits drift from the EDM and need detection |
| **2C** Scripted features | Shape computed by our Python code inside FreeCAD (spike variant B) | Rejected: fails silently without our module |

The company uses CATIA (§12.1); CATIA users receive STEP, which has no parameters in either option. Editing native FreeCAD files only matters if FreeCAD is used in production (X-04, open).

## Decision

1. **Option 1B.** The hopper template becomes a **plan generator** in the ESP domain package. The worker executes plans of general weldment operations and contains no equipment-specific geometry.
2. **Option 2A** for Phase 1 and the prototype. The parametric definition of a generated model is its recorded input set (later the EDM) plus the plan generator version; the FCStd file is a generated, inspectable output. **2C** is rejected. **2B** is revisited when X-04 is decided, and only if hand-editing native FreeCAD files is a real need.
3. This answers the open question of 20 Nov: yes, with the spec wording change below.

### Operation plan, version 1

A JSON document, validated by a Pydantic model on the platform side and executed by a generic executor in the worker. Each operation has an ID, and each part carries the metadata the BOM, flat patterns and drawings need (part name, role, material, thickness or section, quantity group):

| Operation | Inputs (mm, global coordinates) |
|:---|:---|
| `plate` | Closed planar 3D outline, thickness, side to which the thickness is added |
| `profile` | Section reference (catalogue), start and end point, roll angle, optional end-cut planes |
| `tube` | Section reference, start and end point |
| `cut` | Target part, half-space (point, normal) or prism (outline, depth) – mitres, clipping, openings |
| `group` | Named sub-assembly of parts (for drawings and the BOM) |

Operations are added only when a genuinely missing general capability is needed (GE-04 rule), with tests; for example an `opening` for inspection doors in step 6 may be a `cut` with a prism. Naming and result conventions follow the CAD tool design notes in ADR-0001 so the same operations can later be exposed through the CAD MCP service (Phase 6).

Independence of the checks is kept: the plan generator derives the geometry, and the existing `calculation.py` keeps calculating it separately; the model is still checked against the calculation.

### Migration steps

Each step keeps the reference case and the 12-variant sweep at "all checks pass":

1. Plan schema v1 and a generic executor in the worker (`iaiep_worker/operations.py`), next to the template.
2. Move the outline and placement logic of `hopper_geometry.py` and `hopper_profiles.py` into `iaiep_esp.hopper.plan`, which emits a plan.
3. Run both paths and compare geometry signatures, BOM, flat patterns and drawing checks until identical, then remove the template's geometry code from the worker.
4. Drawing definition: the views and critical dimensions now chosen in `esp_hopper._make_drawing` move into a drawing definition delivered with the plan (§12.7); the worker's drawing code becomes generic.
5. Step 6 accessories are built directly as plan operations.
6. Add GE-04 cases (a different panel arrangement, a pyramidal hopper with a different tier division) as data-only tests.

## Consequences

- GE-02 to GE-04 become testable as data changes; the worker can serve later components (conveyor, casing) without equipment code.
- Two implementations remain on purpose (plan generator and independent calculation). The worker no longer holds a third.
- Effort: steps 1–3 are a refactoring of existing, tested code; step 4 is the largest change. Accessories (step 6) wait until step 1 is done, so they are not written twice.
- The native FCStd file is not editable by changing parameters in FreeCAD. Users change inputs and regenerate. This must be stated in the spec:
  - §3.5 and §12.1: "editable" for generated models means *regenerable from the recorded EDM, operation plan and software versions*; the native file must open, show all parts and allow inspection and measurement. Parameter-editable native files are an option tied to X-04.
- The `Parameters` spreadsheet in the native file stays a read-only copy of the inputs, labelled as such.

## Approval

- Product owner accepted 1B and 2A and the spec wording change on 2026-11-23 (spec §3.5, §12.1).
- No engineering-owner decision is needed; engineering rules and criteria are unaffected.
